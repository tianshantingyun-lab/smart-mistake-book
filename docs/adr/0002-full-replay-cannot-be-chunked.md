# 全量重放不可分块

**Status:** accepted (2026-09-12)

全量重放必须对**整份账本一次算完**，不得切成前缀块、逐块提交中间检查点再继续。
理由不是性能，是正确性：**修正（correction）是追溯生效的**——
它作用于自己指名的那次作答，而那次作答在账本里排在它之前。前缀重放会让那次作答
先带着未修正的证据落库，之后无论怎么续算都改不回来。

还有一条更硬的理由：修正根本进不了增量路径。批次加载器一读到修正行就直接要求全量重放，
所以分块重放推到修正处会**再次**拿到同一个要求——它连那个切分点都过不去。

## Considered Options

**分块重放 + 中间检查点。** 被否决，如上：既不等价、又推不动。

**给重放加时间预算，超时放弃。** 被否决：放弃的语义与「这次重放没发生」不同，
会留下一个部分推进的检查点，用户看不到任何差别却已经拿到不一致的数据。

## Consequences

- 账本一旦超出能承受的规模，唯一诚实的结果是**显式失败并保留旧检查点**，
  而不是部分重放。这个失败的上界取多少，不属于本决定的范围。
- 这条约束把「修正」的成本与账本规模绑在一起：每一次修正都会引发一次
  **同步的、无界的**全量重放。任何让修正变频繁的产品改动，都要先看这一条。
- 投影版本升级同样强制所有既有安装走这条路。所以这条约束是**升级路径的基本假设**，
  也是「重放可信化」必须在其他修复之前完成的原因。
