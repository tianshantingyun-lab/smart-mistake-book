# 归因在写入时解析并冻结，历史归因不可事后修正

**Status:** accepted (2026-09-12)

一条证据属于哪个知识点（它的**归因**），在**写入账本的那一刻**就解析完毕，
并逐字段烘焙进该事件的指纹。投影、重放、任何读取路径都**不得**重新解析归因。

因此**历史归因不可事后修正**：改一条已写入事件的归因会改变它的指纹，
而指纹不符会被判为冲突并停止投影——这是设计，不是副作用。

## Considered Options

**读取时解析（投影时去读当前有效的绑定表）。** 看起来更灵活：用户今天重新组织题目，
历史证据就自动跟着走。被否决，因为它会摧毁重放的含义——
同一份账本在用户组织题目**之前**重放给出一种结果、**之后**重放给出另一种结果。
「重放」于是不再是真相的重建，而是调用时刻的函数，而重放正是修复既有安装的唯一手段。

**as-of 语义（用事件时点之前有效的绑定）。** 能恢复确定性，但无法修历史：
新绑定的生效时间晚于事件，as-of 就退化成与写入时判定完全相同。

## Consequences

- 想要修正历史归因，**唯一**不破坏确定性的路是把「修改归因」本身变成一个事件。
  目前没有任何这样的修正类型，修正账本在生产上也没有写入方。
- 因此当前的决策是：**伪归因（以及任何归因缺陷）只从写入层开始修，新的证据不再落伪归因；
  已经落下的历史归因保持原样。** 这不是妥协，是这条约束下唯一自洽的选择。
- 谁若提出「把历史归因改成真绑定」，先读这一条：他会同时需要一种新的修正事件语义。
